# Extending the Phase-2 chemistry layer

This document describes the smallest honest path for adding a fixture, a
parameter-file format, or a capability. It is a developer note, not a roadmap
promise: everything marked **Phase 3+** is unimplemented, and the engine refuses
it with a typed error instead of approximating it.

The normative contract is [`INTERFACE.md`](../INTERFACE.md). The machine-readable
capability boundary is [`capabilities.json`](../reference/capabilities.json),
generated by `tools/register_fixture.py`.

## 1. One normalized schema, one builder

```
parameter file ──extractor (Python, per family)──▶ mdparams 1.0.0 JSON
                                                        │
                          FoundationCore.Chemistry.read_normalized
                                                        │
                                    validate_normalized! (no force math)
                                                        │
                                           build_resolved (one builder)
                                                        │
                                        ResolvedSystem ▸ Factors/SystemContract
```

Units are fixed for the whole record: **nm, kJ/mol, elementary charge, amu**
(`"units": "nm-kj-mol-e-amu"`). The schema has exactly one shape; a new format is
a new extractor, never a new JSON dialect.

| Layer | Owns | Must not |
| --- | --- | --- |
| `tools/extract_amber.py`, `tools/extract_charmm.py` | parsing the parameter file, unit conversion, family conventions, **refusing** unsupported terms | decide factor layout, rescale charges, invent missing terms |
| `julia/src/ChemistrySchema.jl` | key set, units string, 1-based indices, duplicate detection, exclusion/1-4 disjointness, finite numbers, SHA256 shape, charge sum | know anything about force factors |
| `julia/src/ChemistryBuild.jl` | factor selection, topology, exclusions/1-4 scales, protocol wiring | read a parameter file or re-derive parameters |
| `tools/register_fixture.py` | manifest-key validation, extractor invocation, hash/coverage reporting | parse parameters, write the manifest automatically |

Coefficient conventions (they are not interchangeable, see `tools/common.py`):

* bonds/angles: `U = (k/2)(x - x0)^2`; prmtop `K` and CHARMM `K` are doubled on import.
* torsions: `k (1 + cos(n*phi - phase))`, one entry per quadruple with every multiplicity.
* impropers: `k (wrap(phi - phase))^2` in kJ/mol/rad².
* Urey-Bradley: `k (r - r0)^2`, no one-half.

## 2. Register a new `ready` fixture

The example id is `my_fixture`. Nothing here edits `manifest.json`
automatically; the manifest is owned by the fixtures maintainer.

1. **Place the files** inside the repository (e.g. `wrappers/python/tests/systems/`
   or `chemistry/fixtures/`). Paths in the manifest are
   repository-relative and may not contain `..` or start with `/`.

2. **Write a registration spec** (`/tmp/my_fixture.json`) and check it before
   touching the manifest:

   ```json
   {
     "id": "my_fixture",
     "class": "solvated protein",
     "family": "amber",
     "parameter_file": "wrappers/python/tests/systems/my_fixture.prmtop",
     "coordinate_file": "wrappers/python/tests/systems/my_fixture.inpcrd",
     "force_field": "AMBER ff19SB/TIP3P, prmtop from <source>, <license>",
     "status": "ready"
   }
   ```

   ```bash
   ~/.cache/biology-mm/.venv/bin/python \
     chemistry/tools/register_fixture.py --spec /tmp/my_fixture.json
   ```

   The script rejects unknown keys, duplicate ids, ids outside
   `[a-z][a-z0-9_]*`, unknown class/family/status, absolute or escaping paths,
   missing files for `ready`, and — after the extractor runs — a recorded
   SHA256 that disagrees with the actual file. It then prints term counts,
   atom coverage, the extractor's typed refusals, and whether a reference
   artifact already exists. `--json` gives the same report machine-readably;
   `--out /tmp/my_fixture.json` writes the normalized record for inspection.

   `family: "charmm"` additionally needs `--prm` (repeatable) for the parameter
   files. That is a real gap: the manifest has one `parameter_file` key and the
   integration test passes it as `--parm` without `--prm`, so a CHARMM fixture
   cannot be extracted by the consumer test yet (see §7).

3. **Add the manifest entry** (illustration only — do not edit the tracked
   manifest from a tool). `fixtures` is an array; `schema` stays `"1.0.0"`:

   ```json
   {
     "id": "my_fixture",
     "class": "solvated protein",
     "family": "amber",
     "parameter_file": "wrappers/python/tests/systems/my_fixture.prmtop",
     "coordinate_file": "wrappers/python/tests/systems/my_fixture.inpcrd",
     "force_field": "AMBER ff19SB/TIP3P, prmtop from <source>, <license>",
     "status": "ready"
   }
   ```

   Allowed keys are the union already present in the manifest: `id`, `class`,
   `family`, `force_field`, `status`, `parameter_file`, `coordinate_file`,
   `structure_file`, `source_license`, `generator`, `source_structure`,
   `blocker`. Statuses: `ready` (files + reference exist), `generated`
   (produced into the external cache, needs `generator`), `blocked` (needs
   `blocker` naming the exact missing input). Classes are the five Phase-2
   classes; a sixth class is Phase 3+ because the integration test gates on the
   five.

4. **Run the extractor once by hand** to see what will be imported (the
   registration script already does this; the record is cached, not committed):

   ```bash
   ~/.cache/biology-mm/.venv/bin/python \
     chemistry/tools/extract_amber.py \
     --parm wrappers/python/tests/systems/my_fixture.prmtop \
     --crd  wrappers/python/tests/systems/my_fixture.inpcrd \
     --out  /tmp/my_fixture.json --force-field "<same text as the manifest>" \
     --repo-root .
   ```

5. **Build the independent reference** (OpenMM, no network). Add the id to
   `CONFIG_COUNT` and `PROTOCOLS` in `tools/make_reference.py` first — those are
   code, not manifest data — then:

   ```bash
   ~/.cache/biology-mm/.venv/bin/python \
     chemistry/tools/make_reference.py --fixture my_fixture
   ```

   This writes `reference/my_fixture.json` and `reference/my_fixture.f32`
   (Float32, config-major). Commit those two artifacts; the reference is
   generated from the parameter file by OpenMM, never by our engine.

6. **Consumer test.** `julia/test/test_chemistry_fixtures.jl` iterates
   `manifest["fixtures"]` and needs no id list: a new `ready` entry is picked up
   automatically. Its final gate hardcodes the five class ids, so add
   `@assert any(==("my_fixture PASS"), status)` only if the new fixture must be
   gated (a fixture that is legitimately `BLOCKED` on a fresh checkout must not
   be asserted as `PASS`).

7. **Re-run the checks**: `pytest -q chemistry/tools/`, then
   `verify.sh` (Lean + Rocq + Julia). Regenerate the capability
   matrix with `register_fixture.py --only-capabilities` if you changed a
   capability, and update §6 by hand if the boundary moved.

## 3. Adding an adapter without touching force loops

An "adapter" is only ever a new extractor that speaks `mdparams 1.0.0`:

1. Create `tools/extract_<format>.py`; import `common` helpers
   (`validate_record`, `write_record`, `finish`, `fatal`, `sha256_file`) instead
   of re-implementing them.
2. Emit every top-level key, all term indices 1-based, in parameter-file atom
   order, and `net_charge = sum(charges)`.
3. Convert to the fixed units and the coefficient conventions in §1. Verify one
   small system against OpenMM once; do not guess a factor of two.
4. Refuse unsupported content with `fatal("unsupported_term", ...)` — never
   diagonalize, drop, or approximate a term silently.
5. Add tests to `tools/test_extractors.py` (round-trip, one refusal, one
   coefficient check).

No change to `ChemistryBuild.jl`, `ChemistryFactors.jl`, or a force loop is
needed for a term that already exists. If the new format needs a term with no
factor (e.g. a 10-12 wall), that is **not** an adapter change: it needs a new
factor with analytic gradients, a schema field, builder wiring, validator rules,
and finite-difference tests — Phase 3 (see §7).

## 4. Offline core tests vs optional heavy references

| Tier | What runs | Inputs |
| --- | --- | --- |
| Offline core | `tools/test_extractors.py`, `tools/test_register_fixture.py`, `julia/test/test_chemistry_{schema,build,factors,cmap,diagnostics,mutations}.jl` | repository files only; no network |
| Optional heavy | `julia/test/test_chemistry_fixtures.jl` | external prmtop/inpcrd or generated cache plus committed references |
| Optional generator | `tools/make_reference.py` | OpenMM; writes `reference/*` |

Offline tests must pass on a fresh checkout. The heavy suite reports missing
inputs as `BLOCKED` and never as `PASS`; `register_fixture.py` follows the same
rule (a missing reference is reported `false`, not inferred). The registration
test uses a synthetic 6-atom methanol record so it needs neither ParmEd nor
fixture caches; its Julia leg skips when no Julia binary is present.

## 5. Versions and provenance

* `schema` is `"1.0.0"`; `ChemistrySchema.jl` refuses a different **major**
  version. Units are the exact string `"nm-kj-mol-e-amu"`.
* `provenance` has exactly eight keys: `source`, `force_field`,
  `source_sha256`, `coordinate_source`, `coordinate_sha256`, `generator`,
  `generator_version`, `notes`. Hashes are 64 lowercase hex characters and are
  checked against the actual files by `register_fixture.py`.
* `generator`/`generator_version` identify the extractor that produced the
  record (`chemistry/tools/extract_*.py`, currently `1.0.0`).
* `manifest.json` carries its own `schema` (`1.0.0`); `capabilities.json` carries
  `schema`, `generated_at`, `generator`, and one row per `(family, term)` with
  `owner` and `evidence`.
* `ResolvedSystem` has `RESOLVED_SCHEMA_VERSION`; a major mismatch is refused.
* Never write a timestamp or host path into the normalized record: it is
  deterministic (`sort_keys`, `separators=(",", ":")`, no NaN/Inf, trailing
  newline).

## 6. Capability matrix

Statuses follow `capabilities.json`: **supported** = implemented and exercised by
the fixture suite; **partial** = only the stated narrow path; **refused** = a
typed error instead of an approximation.

| Term | AMBER | CHARMM | Owner |
| --- | --- | --- | --- |
| harmonic bonds | supported | supported | `Factors.HarmonicBond` |
| harmonic angles | supported | supported | `Factors.HarmonicAngle` |
| Urey-Bradley | supported (empty for plain prmtop) | supported | `ChemistryFactors.UreyBradley` |
| proper multi-term torsions | supported | supported | `ChemistryFactors.MultiPeriodicDihedral` |
| harmonic impropers | partial (only prmtops written by `ChamberParm`); AMBER periodic "improper" `DIHEDRALS` entries stay in `dihedrals`, as OpenMM does | supported (`psi_k`/`psi_eq`) | `ChemistryFactors.HarmonicImproper` |
| periodic CMAP | supported | supported | `ChemistryCMAP.CMAPCorrection` |
| 1-2/1-3 exclusions | supported | supported | `ChemistrySchema.jl` `exclusions` |
| 1-4 Coulomb/LJ scaling | supported (`1/SCEE`, `1/SCNB`) | supported (1.0) | `ChemistryFactors.PairTableNonbonded` |
| 1-6-4 `-C/r^4` | supported (`LENNARD_JONES_CCOEF`) | refused (no such term) | `ChemistryFactors.PairC64Table` |
| NBFIX / off-diagonal LJ | refused | refused | `extract_amber.check_nbfix`, `extract_charmm.check_nbfix` |
| 10-12 (HBOND) | refused | n/a | `extract_amber.check_hbond` |
| virtual sites / lone pairs | refused at execution (carried in the record) | refused at extraction | `SystemContract._refuse_virtual_sites` |
| triclinic nonbonded | refused (geometry import only) | refused | `ChemistryBuild.build_resolved` |
| PME | supported (orthorhombic) | supported (orthorhombic) | `PME.jl` |
| NPT | partial (isotropic volume move) | partial (isotropic) | `MonteCarloBarostat.jl` |

`register_fixture.py --only-capabilities` re-verifies every `owner`/`evidence`
substring and fails rather than emit a claim it cannot ground.

## 7. Phase 3+ (not implemented, deliberately refused)

* **NBFIX / pair-specific LJ mixing**: schema v1.0.0 has no pair-specific
  sigma/epsilon, and `StreamedLJ` would need a pair table. Refused at import.
* **10-12 (HBOND) potential**: no factor, no gradient, no schema field. Refused.
* **Virtual-site execution**: the record carries linear/planar/average sites,
  but positions are not reconstructed in energy/forces. `SystemContract` throws
  `UnsupportedCapability(:virtual_sites)`.
* **Triclinic nonbonded**: `StreamedLJ`/`PME` are orthorhombic-only. A triclinic
  cell is imported for geometry inspection and refused for execution, never
  flattened.
* **Anisotropic / triclinic NPT**: only isotropic volume moves exist.
* **Multi-file CHARMM parameter sets in the manifest**: needs a manifest key for
  a parameter-file list (Phase 3); today `register_fixture.py --prm` can verify
  such a system, but the consumer test cannot extract it.
* **A sixth fixture class** and anything that would require changing the
  five-class gates.
* **A plugin framework**: not planned. One normalized schema plus one builder is
  the extension model; new formats are new extractor files, new physics is a
  factor + schema + builder change gated on finite-difference tests.
